## 4. What the crosswalk has already falsified

The following possible positioning claims should be treated as **withdrawn or unsupported** unless a later comparison supplies much stronger evidence:

1. TRACE is distinctive because it separates records/descriptions/models from the world or work.
2. TRACE is distinctive because it keeps evidence, assurance, authority and permission separate.
3. TRACE is distinctive because it preserves unknowns/currentness.
4. TRACE is distinctive because it considers reversibility, time windows or hard-to-reverse action.
5. TRACE is distinctive because it preserves multiple affected scopes or challenges omitted affected entities.
6. TRACE is distinctive because it records residual loss / accepted loss.
7. TRACE is distinctive because it carries a problem through a transformation/decision/work path.
8. TRACE is distinctive because it can represent ethical conflicts across scopes or levels.
9. TRACE is distinctive because it says formal conformance is not world truth.
10. TRACE is distinctive because it supports stop/handoff instead of compulsory full formalization.

These are still important TRACE properties. The falsified part is **uniqueness**, not usefulness.

```text
NOT_UNIQUE != USELESS
OVERLAP != IDENTITY
REDUNDANT_CONCEPT != REDUNDANT_COMPILATION
```

## 5. Surviving frontier hypothesis: TRACE as compiled attention profile

A more defensible working hypothesis is:

> TRACE may be a compact, coupled **attention / anti-compression profile** for decision-relevant transitions under uncertainty, rather than a claim to possess a general reasoning ontology unavailable elsewhere.

Under this hypothesis, TRACE's contribution would not be that FPF or another sufficiently expressive framework *cannot* represent affected scopes, evidence, routes, clocks, burdens, residue, selection, authority and future options. It would be that TRACE makes a selected subset of those distinctions jointly available in one bounded transferable object with a predictable activation surface.

This is analogous to compilation, not ontological priority:

```text
BROADER_PATTERN_LANGUAGE
    -> select recurring transition/harm/correction distinctions
    -> compile into bounded reading profile
    -> reduce search/routing burden
    -> accept loss of generality
```

But compilation is valuable only if the compiled artifact earns its cost.

```text
COMPACTER != BETTER
DEFAULT_ACTIVATION != CORRECT_ACTIVATION
MORE_GUARDS != FEWER_OMISSIONS_IN_PRACTICE
ONE_PACKET != LOWER_TOTAL_BURDEN
```

TRACE must therefore be tested on **omission and burden together**.

## 6. Strongest unresolved semantic candidates

This pass leaves only a small number of plausible semantic remainders, and none is yet established:

### R1 — explicit correction-window construction

TRACE [9.1]-[9.5] couples pathway binding, affected scope, correction route/capability, target boundary, temporal basis, precedence/acyclicity, feasibility and window-status ceilings into a derived correction-window object.

FPF clearly has temporal, constraint, route, option, evidence and irreversible-use machinery. It is unresolved whether a native FPF use can produce the same strong correction-window result without assembling equivalent local machinery.

**Test:** same time-critical case; ask whether each framework can distinguish `open`, `closed`, and `unknown` without optimistic parallelism, clock-basis error, hidden alternative routes or post-result boundary selection.

### R2 — compact access/custody separation

TRACE explicitly distinguishes evidence state from receiver access/custody/disclosure authority. FPF has evidence, publication, source-use, permission and reliance machinery, but this pass did not establish a one-step native equivalent.

**Test:** evidence exists but is inaccessible to one receiver and disclosure is separately unauthorized. Compare whether both frameworks prevent `UNAVAILABLE_TO_ME -> UNKNOWN_TO_WORLD` and `CAN_ACCESS -> MAY_DISCLOSE` collapse at similar burden.

### R3 — liveness/witness cause ceiling

TRACE has a compact operational ceiling separating lost heartbeat/reply/status from cause, and external/separate witness from independent evidence. FPF has recovery/currentness/evidence machinery, but this pass did not establish exact functional equivalence.

**Test:** interrupted worker / missing response / stale witness case. Compare what each permits a reviewer to conclude.

These are **candidate remainders**, not claims of novelty.

## 7. Falsifiers for the compiled-profile hypothesis

### FPF-1 — same structure, less burden

If a competent FPF use consistently preserves all consequential TRACE distinctions on representative cases with less reading, fewer required fields, less routing and no additional material omissions:

```text
TRACE_COMPILED_PROFILE -> NARROW / REPOSITION / REMOVE DUPLICATION
```

### FPF-2 — TRACE catches omitted load-bearing dimensions

If matched users repeatedly stop under FPF with a locally sufficient result that omits a consequential affected-scope / target-set / correction-window / burden / residue relation, while TRACE exposes it before the decision and the extra finding changes review, handoff or correction:

```text
TRACE_COMPILED_ACTIVATION -> CANDIDATE PRACTICAL DELTA
```

This is not proved by one anecdote.

### FPF-3 — more structure, no decision effect

If TRACE produces more fields/distinctions but the added structure changes no material decision, review, handoff, correction or later reconstruction:

```text
MORE_TRACE_STRUCTURE -> NO_MATERIAL_DELTA_ON_CASE
```

### FPF-4 — TRACE burden creates its own failure

If the TRACE reading takes enough effort that it delays action, shifts proof burden onto affected parties, reduces honest population of fields, or encourages checkbox completion:

```text
TRACE_BURDEN -> NEGATIVE PRACTICAL RESULT
```

### FPF-5 — only terminology differs

If the alleged remainder disappears after mapping to FPF's native object rather than TRACE vocabulary:

```text
VOCABULARY_DIFFERENCE -> REDUNDANCY FINDING
```

### FPF-6 — hidden local framework inside FPF

If reproducing TRACE under FPF requires authoring a stable local package that selects essentially the same recurring fields and rules, then semantic redundancy may coexist with a legitimate profile-level need:

```text
GENERAL_FRAMEWORK_CAN_EXPRESS_TRACE
AND
REPEATED_USE_REQUIRES_RECOMPILING_SAME_SUBSET
-> PROFILE/PRODUCT VALUE POSSIBLE
```

That outcome would favour modest positioning: TRACE as a specialised reusable profile, not as a superior universal ontology.

## 10. FPF framework-architecture pressure

The full pinned FPF source contains an explicit framework ecosystem architecture. This matters because it means even the hypothesis `TRACE = specialised compiled profile` is not automatically outside FPF's own product model.

Relevant FPF surfaces:

- `E.4` separates FPF Core from domain/local principle frameworks and adjacent maintained products.
- `E.4.PFAD` chooses among five outcomes:
  1. new or revised framework;
  2. contribution to an existing framework;
  3. maintained non-framework product;
  4. thinner publication/access route;
  5. no new maintained product now.
- `E.4.DPF` is an authoring/publication spine for domain and local FPF-grounded frameworks.
- `E.4.DPF.DA` evaluates domain scope, source basis, Core dependency, package form, coverage, relation records, publication/access, refresh and adoption utility.

FPF's own PFAD rule explicitly warns that a small coherent authoring slice can be mistaken for a field-scale pattern language. A new/substantially revised domain framework should identify a first user/use that needs no unpublished context, connected problem families, what FPF/existing frameworks already provide, what remains uncovered, serious cheaper alternatives, a representative cross-problem use, evidence limits and a refresh trigger.

This is an appropriate hostile architecture test for TRACE even though TRACE was independently developed and is not currently an FPF-grounded DPF.

```text
INDEPENDENT_ORIGIN != INDEPENDENT_FUNCTION
EXISTING_RELEASE != FUTURE_ARCHITECTURE_JUSTIFIED
FRAMEWORK_SHAPE != FRAMEWORK_SCALE_EARNED
```

## 11. Stronger current frontier

The frontier is no longer:

```text
CAN TRACE REPRESENT THINGS OTHER FRAMEWORKS CANNOT?
```

It is:

```text
DOES THIS PARTICULAR COMPILATION OF DISTINCTIONS
CAUSE A BOUNDED RECEIVER TO NOTICE AND PRESERVE
CONSEQUENTIAL STRUCTURE IT WOULD OTHERWISE LOSE,
AT LOWER TOTAL COST THAN ROUTING THROUGH A BROADER SYSTEM?
```

This is an empirical/product-architecture question.

It creates a sharper possible identity for TRACE:

```text
TRACE = candidate specialised transition-attention compiler
        + portable structural carrier
        + anti-compression defaults
        + explicit claim ceilings
        + correction-window emphasis
```

That description is deliberately provisional. `compiler` here is analogy, not a new TRACE primitive or software claim.

A specialised object can be worthwhile even when every constituent concept exists elsewhere. Examples outside this project include checklists, profiles, safety cases, domain-specific languages and protocols whose value lies in selection, arrangement, interoperability or activation rather than conceptual novelty.

But TRACE must earn that role through use.

## 13. Why this matters

If TRACE survives only as a smaller, sharper, portable compilation of already available reasoning capabilities, that is still meaningful if the compilation measurably reduces consequential omission at acceptable burden.

If a mature neighbouring method preserves the same load-bearing structure with less cost, the project should learn from that rather than protecting TRACE's status.

If the useful result is interoperability rather than independence, preserve ancestry and build the bridge without pretending equivalence or subordination.

If the useful result is to stop expanding TRACE, preserve the released object and move the wider purpose through Mechanical Ethics, field practice and better existing tools.

```text
PROJECT PURPOSE != TRACE NOVELTY
TRACE SURVIVAL != PROJECT SURVIVAL
FAILED UNIQUENESS CLAIM != FAILED PURPOSE
BETTER EXISTING METHOD -> LEARN / REUSE / NARROW
PRESERVATION != PERMANENT EXPANSION
```
